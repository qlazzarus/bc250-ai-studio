# LLM 모델 전환: 배포 전 미비 사항

검토 기준: 현재 작업 디렉터리의 코드와 테스트, 사용자가 제공한 운영 설정. 운영 서버의 파일을 직접 읽거나 변경하지 않았습니다. 이 문서는 남은 작업 목록이며 배포 지시서가 아닙니다. **현재 상태로는 모델 전환 기능을 운영에 활성화하면 안 됩니다.**

## 먼저 해결해야 하는 배포 차단 항목

1. **실제 배포 경로를 검증해야 합니다.** 전용 HTTP API → 인증된 Unix 소켓 → 단일 root 작업자 → 전환·복구의 후보를 연결하고 전환은 기본적으로 껐습니다. 읽기 전용 구형 소켓 후보와 별개의 신규 unit이며, 실제 systemd·권한·SELinux 환경에서는 아직 실행하지 않았습니다.
2. **기존 수동 전환은 안전 절차를 우회합니다.** 운영자는 이 우회를 허용하기로 했습니다. 자동 전환 결과는 기존 활성 모델 설정에 반영되어 `ai-model status`에서도 확인되어야 하며, 설치 모델 목록은 `ai-model list`와 일치해야 합니다. 수동 작업이 자동 작업과 겹치면 보호되지 않는다는 한계도 명시해야 합니다.
3. **gate pause의 실제 이전이 남아 있습니다.** opt-in 소유권 모드는 관리자·Studio·전환 키와 hold를 분리하며 재시작 시 `startup` hold를 둡니다. 구버전 Studio와 기존 관리자는 단일 `paused` 계약을 사용하므로 gate·Studio·전환 기능·관리자 제어·복구를 함께 이전하고 실제 운영과 같은 조건에서 시험해야 합니다.
4. **GPU 잠금과 복구 차단은 자동 작업에 아직 적용되지 않았습니다.** 새 root 소유 잠금 경로, Studio의 전환 journal 확인, root 작업자의 생명주기 잠금은 후보 단계입니다. Studio와 자동 전환은 같은 inode와 복구 차단 기록을 사용해야 합니다. 운영자가 허용한 수동 우회는 이 보호 범위 밖입니다. 이전 경로와 새 경로를 동시에 사용하면 안전하지 않습니다.
5. **전환 중 종료와 장애 복구는 실제 서비스 경계에서 검증되지 않았습니다.** 후보 코드는 시스템 명령 결과 불명, journal, gate hold, 이전 모델 health를 다루지만 systemd·root 서비스·Studio를 묶은 실제 프로세스 종료 시험과 운영 복구 절차가 없습니다. 복구가 확인되기 전 gate를 열지 않아야 합니다.
6. **기존 배포 경로가 이 변경을 처리하지 않습니다.** 운영자는 직접 수정·배포할 예정이므로 한국어 수동 배포 명령과 검증·롤백 절차를 준비합니다. 저장소 워크플로에서 `main` push 자동 배포를 제거했지만, 기존 수동 워크플로와 배포 스크립트는 Studio만 중지하고 gate를 재시작하지 않으므로 새 구성에는 사용하지 않습니다. 변경이 아직 원격에 반영되지 않았으므로 현재 운영 중인 자동 배포 설정은 별도로 확인해야 합니다.

## 운영자 회신 검토

| 번호 | 회신과 판단 | 남은 조치 |
| --- | --- | --- |
| 1 | 배포 후 실제 환경에서 시험하기로 함 | 연결 후보는 구현했으며 실제 systemd·격리 환경 통합 시험이 필요합니다. 배포 후에는 운영자가 직접 시험합니다. |
| 2 | 기존 수동 전환의 안전 절차 우회를 허용함. 자동 전환 결과가 기존 `ai-model` 명령에도 반영되어야 함 | 기존 `active-model.conf`와 `models/*.conf`를 공통 기준으로 사용하고, 자동 전환 성공·복구 후 `status`와 `list`의 결과를 검증합니다. 수동 변경이 자동 작업과 겹칠 때 충돌 가능성을 명시합니다. |
| 3 | gate pause 소유권을 개선하기로 함 | 세 가지 전용 키와 hold별 제한, 재시작 시 시작 hold 및 복구 확인 기능을 추가했습니다. 실제 권한·기존 계약 이전·장애를 검증합니다. |
| 4 | 현재 관리자는 한 명이므로 이 우려를 수용함 | 관리자 수가 하나여도 자동 이미지 작업과 모델 전환은 동시에 실행될 수 있습니다. 자동 경로의 공유 잠금·복구 차단은 필수이며, 허용된 수동 우회는 예외로 기록합니다. |
| 5 | 배포 후 실제 환경에서 시험하기로 함 | 실패·강제 종료는 먼저 격리 환경에서 시험하고, 실제 서비스 검증과 복구 절차를 준비합니다. 복구 미확인 시 gate를 열지 않습니다. |
| 6 | 운영자가 직접 수정·배포하며 명령을 원함 | [수동 배포 초안](./LLM_MODEL_SWITCH_DEPLOYMENT_DRAFT.md)에 준비 명령과 구성·순서를 추가했습니다. 실제 설치·재시작·롤백 명령은 Fedora 격리 시험 후 확정해야 합니다. |

### 수동 전환과 현재 모델

- 수동 전환 후에는 프로세스 내부 캐시만 믿지 않고 `active-model.conf`를 다시 읽어 관리 이름을 확인해야 합니다. 설정값은 전환 중 실제 로드보다 먼저 바뀔 수 있으므로 설정상 선택 모델과 실제 로드된 GGUF ID, health를 구분합니다. `/v1/models`의 경로 ID를 관리 이름으로 취급하지 않습니다.
- 기존 수동 명령은 공유 잠금과 gate drain을 거치지 않습니다. 관리자가 한 명이어도 자동 이미지 생성 또는 진행 중 LLM 요청과 겹칠 수 있으며, 별도 확인만으로 경쟁 상태를 없앨 수 없습니다. 수동 작업을 수행할 때는 자동 작업과 요청을 중지하고 상태를 확인하는 운영 절차가 필요합니다. 이 예외는 자동 전환의 안전성을 대신하지 않습니다.
- 자동 전환은 기존 `/opt/ai/config/active-model.conf`의 `ACTIVE_MODEL`을 갱신하고, 모델 목록은 기존 `/opt/ai/config/models/*.conf`를 기준으로 합니다. `ai-model status`는 활성 이름을 표시하고 `ai-model list`는 설치된 이름을 나열하므로 전환 자체가 목록을 바꾸지는 않습니다. 전환 실패 후 이전 모델 복구 시에도 활성 설정이 복구된 모델과 일치해야 합니다.
- 후보 registry는 동일한 활성 설정을 읽고 원자적으로 교체하며 새 root 작업자 및 HTTP 경로에 연결됐습니다. `ai-model status`·`list`, 관리 API와 실제 로드 모델을 함께 비교하는 실제 설정의 성공·복구 통합 시험이 필요합니다. client에서 모델 설정값을 수정하는 기능은 이번 요구에 포함되지 않습니다.

### 수동 배포 준비를 위한 읽기 전용 확인

아래 명령은 서비스를 변경하지 않고 비밀 환경변수를 출력하지 않습니다. 실제 설치·재시작·롤백 명령은 전환 경로와 설정이 완성된 뒤 작성합니다.

운영자 회신: Studio는 `ai-studio:ai-studio`, `ProtectSystem=strict`, `NoNewPrivileges=yes`, `RuntimeDirectoryPreserve=no`입니다. gate는 같은 계정으로 활성 상태이며 llama-server는 활성 상태, `Job=` 비어 있음, `KillMode=control-group`으로 확인됐습니다. 이는 조회 시점의 상태입니다. 공유 잠금 경로는 Studio의 쓰기 예외와 별도 수명 관리가 필요하며, Studio의 `NoNewPrivileges`는 root 권한 획득 수단으로 사용할 수 없습니다.

추가 회신: Studio의 `ReadWritePaths`는 `/opt/ai-studio-data`이고 gate는 쓰기 예외가 없으며 두 서비스 모두 `ProtectSystem=strict`, `NoNewPrivileges=yes`입니다. SELinux는 `Enforcing`입니다. `/opt/bc250-ai-studio`와 `.venv`는 root 소유이나 `backend` 및 `backend/app`은 이름으로 해석되지 않는 UID/GID 소유입니다. 이름 미확인 자체가 악성 또는 쓰기 가능을 뜻하지는 않지만 root 서비스의 코드 신뢰 경계를 확정할 수 없으므로 숫자 UID/GID, ACL, 실제 코드·가상환경의 소유권과 실행 경로를 확인해야 합니다. root 전용 코드 경로와 배포 방식, gate 영구 상태 저장 경로의 쓰기 허용 및 SELinux 레이블·정책은 배포 전에 검증합니다. 기존 배포 스크립트는 `cp -a`로 배포 파일을 복사하므로 소유권이 보존될 수 있어 root 작업자의 코드 무결성을 자동 보장하지 않습니다.

숫자 권한 확인: `backend`와 `backend/app`은 UID/GID 1001 소유, 모드 0755이며 추가 ACL 항목은 없습니다. UID 1001은 해당 디렉터리에서 파일을 교체할 수 있으므로 이 경로를 root 작업자의 신뢰된 코드 경로로 사용해서는 안 됩니다. 해당 UID가 현재 계정 이름으로 해석되지 않아도 소유권에 따른 권한은 남습니다. 상위 `/opt/bc250-ai-studio`와 `.venv` 디렉터리는 root 소유 0755이나 내부 파일·링크·ACL까지 검증된 것은 아닙니다. 검사한 경로의 SELinux 유형은 `usr_t`, 가상환경 Python의 실경로는 `/usr/bin/python3.14`입니다. 이 값만으로 새로운 서비스의 SELinux 접근이나 모든 의존성의 Python 3.14 호환성이 입증되지는 않습니다.

```bash
systemctl show --no-pager bc250-ai-studio.service \
  -p User -p Group -p RuntimeDirectory -p RuntimeDirectoryPreserve \
  -p ProtectSystem -p NoNewPrivileges
systemctl show --no-pager bc250-llm-gate.service \
  -p User -p Group -p FragmentPath -p DropInPaths -p ActiveState
systemctl show --all --no-pager llama-server.service \
  -p LoadState -p ActiveState -p MainPID -p Job -p KillMode
```

## 1. 모델 전환과 공유 GPU 잠금

- [ ] `/run/bc250-gpu/gpu.lock` 후보를 root 소유 디렉터리에 사전 생성하고 Studio와 root 작업자가 실제로 같은 파일을 잠그는지, 소유권·그룹·ACL·systemd 쓰기 경로와 부팅 시 생성 순서를 확인합니다. 저장소의 `STUDIO_GPU_LOCK_SECURE_PRECREATED`는 기본적으로 꺼져 있습니다.
- [ ] 기존 `/run/bc250-ai-studio/gpu.lock` 사용자를 모두 중지한 뒤 새 경로로 함께 이전하고, 중지·재시작 중 잠금 파일의 삭제·교체를 방지합니다. `RuntimeDirectoryPreserve=yes`만으로 모든 소유권 문제가 해결되지는 않습니다.
- [ ] 모델 작업자의 별도 생명주기 잠금 파일을 root 전용으로 만들고, 실제 데몬이 안전한 사전 생성 파일을 열도록 연결합니다. GPU 잠금과 작업자 잠금이 다른 파일이어야 합니다.
- [ ] Studio 외의 GPU 프로세스와 우회 경로를 확인합니다. 자동 경로는 잠금·전환 기록을 사용해야 합니다. 운영자가 허용한 수동 스크립트와 직접 systemctl 조작은 예외이며 flock이 강제하지 않으므로 충돌 가능성을 운영 절차에 기록합니다.
- [ ] 실제 이미지 작업과 전환의 경쟁, 동시 전환 거절, 취소·종료 및 프로세스별 inode 일치를 별도 프로세스와 실제 배포 권한으로 검증합니다.

## 2. 이미지 대기와 Studio 복구

- [ ] 외부 잠금 경합 시 이미지가 재시도되고 수동 실행 허가가 유지되는 기존 변경을 실제 배포 구성에서 검증합니다. 잠금 접근 오류와 실제 이미지 생성 오류는 실패 원인으로 구분해야 합니다.
- [ ] 전환 journal의 **유효한 미복구 기록**은 대기로 처리하지만 파일 누락·손상·권한 오류는 현재 일반 오류가 되어 이미지 작업이 실패할 수 있습니다. 상태 화면에 원인과 복구 필요를 명확히 표시하고 운영 방침에 맞게 처리합니다.
- [x] `GPUManager.journal()`의 기존 단계가 새 단계를 덮어쓰던 오류를 수정하고 단계 갱신을 테스트했습니다. 실제 배포 후 복구·상태 확인은 남았습니다.
- [ ] legacy 경로는 사전에 관리자 pause가 보이면 보존하고, pause 응답이 유실되어 소유권이 불확실하면 자동 resume 대신 복구 필요로 남기도록 수정했습니다. 단일 불리언 계약상 동시 관리자 변경과 응답 유실을 완전히 구분할 수 없으므로 소유권 방식으로 이전하고, 불확실한 레거시 기록의 관리자 복구 절차를 검증해야 합니다.
- [x] 원래 LLM이 비활성이어도 gate 복구 실패 시 복구 필요 상태를 유지하고 재시도하도록 수정·테스트했습니다. 실제 gate 장애는 별도 검증이 필요합니다.
- [ ] 소유권·공유 잠금·journal·전용 조율 키는 기본값이 꺼져 있습니다. root 작업자는 실제 Studio의 전용 조율 응답과 gate 역할을 매 전환 전 확인하도록 보강했습니다. 실서버에서 일부만 이전한 조합이 차단되는지 검증해야 합니다.

## 3. gate 일시정지 소유권과 요청 drain

- [ ] gate 상태 파일의 사전 생성, 소유권·권한, 저장 위치·백업과 재부팅 시 복원 방법을 확정합니다. 파일이 없거나 손상됐을 때와 디스크 쓰기·원자적 교체·디렉터리 동기화 실패 시 안전한 상태가 유지되는지 별도 프로세스로 시험합니다.
- [ ] hold 생성·해제 요청의 응답이 유실된 경우와 gate 강제 종료·재시작을 시험합니다. 현재 쓰기 실패 시 같은 gate 프로세스에서는 hold를 유지하지만, 영구 저장 여부가 불확실한 상태에서의 재시작 안전성은 별도로 입증해야 합니다.
- [ ] 소유권 모드에서 관리자·Studio·전환 작업자의 키와 hold 권한을 분리했습니다. 실제 UID, 자격 증명 저장 및 소유권 모드 이전을 검증합니다. 레거시 모드는 여전히 공유 키를 사용합니다.
- [ ] 기존 `/control`의 `paused` 호출과 새 hold의 호환성을 적용 순서와 함께 검증합니다. 구버전 Studio는 다른 hold 때문에 `paused=true`가 유지되는 정상 상황을 오류로 해석할 수 있습니다.
- [ ] 모든 LLM 호출이 gate를 경유하는지 확인하고, gate의 `active_requests=0`과 llama 슬롯 유휴를 함께 검증합니다. gate 재시작, 클라이언트 연결 종료, upstream 응답 버퍼링 및 직접 8080 접근의 영향도 시험합니다.

## 4. root 권한과 제한된 모델 관리 인터페이스

- [ ] 구형 읽기 전용 후보와 별도로 [root 작업자 조립](../backend/app/services/model_control_runtime.py), [Unix 소켓 연결](../backend/app/services/model_control_bridge.py), [HTTP API](../backend/app/api/remote_model_management.py)를 추가했습니다. 단일 작업자 생명주기와 연결 종료·서비스 재시작을 실제 systemd에서 검증해야 합니다.
- [ ] 기존 `Accept=yes` 소켓은 읽기 전용 후보입니다. 별도로 `Accept=no`, loopback 접근과 제한된 쓰기 경로를 가진 단일 작업자 unit을 추가했습니다. 실제 systemd·SELinux 권한과 장기 작업 종료 정책을 검증합니다.
- [ ] root 서비스가 읽는 코드·가상환경·설정·모델 registry·상위 디렉터리의 소유권, 쓰기 권한, ACL 및 심볼릭 링크를 운영 서버에서 확인합니다. 모델 설정은 root로 `source`되므로 설정 파일을 수정할 수 있는 권한은 root 코드 실행 권한에 가깝습니다.
- [ ] root 작업자는 journal의 부모·파일 소유권·링크·권한을 검사하는 모드로 조립했습니다. 쓰기 시 ACL·SELinux 레이블 변경은 차단합니다. 운영 파일시스템·SELinux에서 이 검사가 정상 동작하는지 검증합니다.
- [ ] 전용 관리 키의 실제 전달·저장·교체 방법과 다른 Studio·gate 키와의 중복 방지를 구현합니다. HTTP 호출자는 고정 단일 관리자이며 ID별 사용자 격리는 아직 없습니다. client 백엔드의 실제 관리자 인증도 별도 확인합니다.
- [ ] 경로·서비스명·임의 명령을 받지 않는 제한된 요청과 peer credential 검증을 읽기·전환·복구 전부에 적용하고, 인증 실패·비인가 호출·잘못된 입력을 통합 테스트합니다.

## 5. 전환 실패와 복구

- [ ] systemctl 재시작 전 서비스의 상태·미완료 job을 확인하고, 재시작 실패·시간 초과 후 systemd 작업이 정말 끝난 뒤에만 이전 모델 복구를 실행합니다. `Restart=on-failure` 자동 재시작과 서비스 비활성·실패 상태도 포함해 검증합니다.
- [ ] 전환 기록을 남긴 뒤, gate hold 확보 직전·직후, drain 중, 활성 설정 변경 직전·직후, systemctl 실행 중, health 확인 중, hold 해제·journal 삭제 사이의 강제 종료와 재시작을 각각 시험합니다.
- [ ] 이전 모델 재시작 실패, 이전 모델 health 시간 초과, 잘못 로드된 GGUF ID, gate 응답 유실·저장 오류가 발생하면 hold와 기록을 유지하고 관리자가 원인을 볼 수 있어야 합니다. 이전 모델 복구가 확인된 drain·재시작·health 실패는 각각 제한된 오류 코드로 구분합니다. 실서버의 실패 경로는 아직 검증하지 않았습니다.
- [ ] journal 없이 `recovery_required`인 경우의 검증 후 정리, 불일치 journal의 root 오프라인 복구, 고아 Studio·전환 hold의 검증 후 해제 후보를 추가했습니다. 독립 관리자 hold, 공통 잠금, Studio·LLM health를 확인하며 DB·journal을 무조건 삭제하지 않습니다. 손상된 상태 및 실제 systemd에서의 복구 절차 검증이 남았습니다. 공개 복구 API는 없습니다.
- [ ] gate 재개와 journal 정리 순서에서 프로세스가 종료되더라도 다른 GPU 사용자가 위험한 상태를 이용하지 못하는지, 특히 모든 사용자의 공통 차단 여부를 검증합니다.
- [ ] `systemctl show`의 정상 실행 시 필드는 사용자 제공 값과 일치합니다. 재시작·실패·자동 재시작 중의 출력은 아직 확인하지 않았고, 운영 모델 전환을 자동 실행해 확인하지 않습니다.

## 6. 모델 이름, 설정 및 client 계약

- [ ] 현재 활성 `gemma4-e4b-hauhaucs`는 설정의 `MODEL_PATH`와 gate `/v1/models` ID가 일치했습니다. 나머지 설치 모델의 설정 문법·경로와 실제 전환 후 ID는 아직 검증하지 않았습니다. 관리 이름과 GGUF ID를 계속 분리합니다.
- [ ] 후보 설정 파서는 단순 리터럴 대입만 지원합니다. 다른 운영 모델 설정에 따옴표·공백·변수 치환 등 지원하지 않는 문법이 있는지 비밀값을 출력하지 않는 방식으로 확인하고, 필요하면 안전한 형식으로 정리합니다.
- [ ] 활성 설정 원자적 교체 시 기존 소유권·모드뿐 아니라 운영 서버의 ACL, SELinux 컨텍스트와 파일시스템 내구성까지 검토합니다. root 소유 설정 경로에 대한 안전한 접근을 보장합니다.
- [ ] [API 계약 후보](./LLM_MODEL_MANAGEMENT_API.md)의 인증·목록·현재 모델·전환·조회·중복 키·오류·상태를 실제 서비스에 연결하고, 사용자에게 보이는 오류 코드 및 복구 안내를 확정합니다. client 브라우저에 gate 키나 서버 관리자 키를 전달하지 않습니다.
- [ ] 현재는 단일 관리자입니다. 사용자 ID별 인증·권한·대화·작업·파일 격리는 [별도 TODO](./USER_ISOLATION_TODO.md)이며 구현된 기능으로 간주하지 않습니다.

## 7. 테스트와 운영 배포

- [ ] 최신 전체 백엔드 테스트와 Ruff, 프런트엔드 lint·빌드를 다시 실행합니다. 로컬 성공은 실제 서버 통합·GPU 검증을 뜻하지 않습니다.
- [ ] root 소유 실제 경로·Unix 소켓·systemd 제한과 프로세스 강제 종료를 격리된 환경에서 통합 테스트합니다. 현재 다수의 root·systemd 동작은 모의 객체나 권한 검사 대체를 사용합니다.
- [ ] 설치·전환 전 변경 파일 목록, root 서비스와 gate·Studio 설정, 상태 디렉터리 생성, 전용 키 발급, 소유권·ACL·SELinux, 서비스 재시작 순서와 호환성 확인 명령을 한국어로 작성합니다. 비밀값을 출력하지 않습니다.
- [ ] 기존 LLM과 모든 호출자를 유지보수 상태로 묶고, 작업 중인 이미지·대화와 이전/새 잠금 사용자 모두가 없는지 확인한 다음에만 경로와 gate 계약을 함께 이전합니다. 서비스가 정상이라고 추측하지 말고 확인합니다.
- [ ] gate 상태, 전환 journal, 작업 DB와 기존 `ai-model`·모델 설정·unit·코드·데이터를 호환되는 단위로 백업하고 롤백 절차를 시험합니다. 구버전 gate는 새 hold를 이해하지 못하므로 복구 확인 없이 구버전으로 돌려 admission을 열면 안 됩니다.
- [ ] 운영자가 직접 실행할 검증 명령과 정상·실패·롤백 판정 기준을 작성합니다. 실제 운영 서버의 모델 전환이나 GPU 작업은 준비 과정에서 자동 실행하지 않습니다.
