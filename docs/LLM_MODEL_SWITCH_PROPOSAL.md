# LLM 모델 전환: 결정 사항과 구현 계획

이 문서는 검토용입니다. 모델 전환 API와 전용 root 서비스는 아직 구현되지 않았습니다. gate의 ID별 일시정지 상태 보관과 Studio 복구 연동은 기본값이 꺼진 기초 구현이며 운영에 활성화할 준비가 되지 않았습니다. `deploy/ai-model-recovery-candidate`는 재시작 실패와 복구 확인만 검토하는 후보이며 단독으로 설치하면 안 됩니다. 단계별 상태는 [작업 계획](./LLM_MODEL_SWITCH_WORKPLAN.md)을 참고합니다.

## 추천하는 사용 방식

1. `bc250-llm-client`에서 관리자만 설치된 모델 목록을 보고 전환을 요청합니다.
2. 이미지 생성이 GPU를 사용 중이면 전환 요청은 기다립니다. 다른 전환이 이미 요청되었거나 진행 중이면 새 요청은 거절합니다. 진행 중인 LLM 요청이 끝날 때까지 기다린 뒤 전환합니다.
3. 전환에 실패하면 이전 모델로 복구하고 정상 응답을 확인합니다. 복구가 확인되지 않으면 LLM 요청을 계속 일시정지하고 관리자에게 복구가 필요하다고 표시합니다.
4. 관리자는 전환 진행 상태와 실패 원인을 확인합니다. 일반 사용자는 모델 변경이나 셸 명령을 실행할 수 없습니다.

## 결정된 사용 방식

| 항목 | 선택 | 다른 선택과 영향 |
| --- | --- | --- |
| 전환 권한 | client의 관리자만 전환 | 모든 사용자 허용은 다른 사용자의 대화와 이미지 작업에 영향을 줄 수 있음 |
| GPU 사용 중 전환 | 대기 후 자동 진행, 진행 상태 표시 | 즉시 거절하면 사용자가 직접 다시 시도해야 함 |
| 동시에 들어온 전환 | 첫 요청을 유지하고 이후 요청은 충돌로 거절 | 여러 요청을 차례로 처리하면 의도하지 않은 연속 전환이 생길 수 있음 |
| 복구가 불확실한 경우 | gate를 닫고 관리자 확인 후 복구 | 자동으로 열면 비정상 모델이나 GPU 충돌 위험이 있음 |
| 기존 수동 전환 | 기존 `ai-model switch`도 같은 안전 절차로 연결 | 기존 명령을 그대로 두면 잠금과 gate를 우회할 수 있음 |

사용자는 위 추천안을 선택했습니다. 현재 사용자는 한 명이며, 지금의 관리자 권한은 향후 사용자 ID별 격리를 구현한 것으로 간주하지 않습니다. 실제 배포와 운영 서버 검증은 코드와 테스트가 준비된 후 별도로 진행합니다. 향후 작업은 [사용자 ID별 격리 TODO](./USER_ISOLATION_TODO.md)에 기록합니다.

## 확인된 운영 환경

- Studio와 gate는 `ai-studio`로 실행되고, `llama-server.service`는 root로 실행됩니다. llama의 `KillMode`는 `control-group`입니다.
- 현재 `ai-studio`에는 sudo 권한이 없습니다. 저장소의 Studio unit에는 `NoNewPrivileges=true`가 있으므로 sudo 권한을 추가하는 것만으로 Studio에서 권한을 올릴 수도 없습니다.
- `/usr/local/bin/ai-model`은 `/opt/ai/scripts/ai-model`을 가리킵니다. 현재 스크립트는 모델 목록·상태·전환을 제공하지만, 즉시 재시작 실패 시 복구를 건너뛸 수 있고 이전 모델 복구 후 health를 확인하지 않습니다.
- `start-llama.sh`는 활성 설정과 모델 설정을 root로 `source`합니다. 확인한 스크립트·설정 파일과 상위 디렉터리는 root 소유이며 그룹과 기타 사용자에게 쓰기 권한이 없습니다. 모델 설정 심볼릭 링크는 발견되지 않았습니다. ACL과 확인하지 않은 경로는 추가 점검이 필요합니다.
- 관리용 모델 이름과 추론 API `/v1/models`에서 보이는 GGUF 경로 ID는 다릅니다. 이 둘을 같은 값으로 취급하지 않습니다. 사용자가 제공한 `gemma4-e4b-hauhaucs`의 `MODEL_PATH`는 gate에서 조회한 현재 ID `/opt/models/gemma4-e4b-hauhaucs/Gemma-4-E4B-Uncensored-HauhauCS-Aggressive-Q4_K_M.gguf`와 정확히 일치합니다. 이는 현재 모델 한 개에 대한 확인이며 다른 설치 모델의 ID나 향후 별칭 설정까지 보장하지 않습니다.
- gate는 현재 `paused` 하나와 진행 중·대기 중 요청 수를 제공합니다. 이 불리언만으로는 누가 일시정지했는지 구분할 수 없습니다.
- 설치된 Studio의 `RuntimeDirectoryPreserve=no`이며 확인 시 `/run/bc250-ai-studio/gpu.lock`은 없었습니다. 파일이 없다는 사실만으로 GPU 사용 여부는 알 수 없습니다. 저장소 템플릿은 `RuntimeDirectoryPreserve=yes`로 변경했으나 서버에는 적용되지 않았습니다.

## 추가 확인이 필요한 사항

구현을 시작하기 위한 추가 비밀값은 필요하지 않습니다. 정확한 배포 절차를 완성할 때 다음을 확인합니다.

- Studio와 gate에 실제 적용된 systemd 설정과 polkit 규칙, 각 서비스의 상태 저장 경로·권한. 환경 파일의 비밀값은 출력하거나 공유하지 않습니다.
- 모든 LLM 사용자가 gate를 경유하는지와 운영자가 현재 수동 전환을 어떻게 실행하는지. gate를 우회하는 호출이나 직접 `systemctl restart`는 조율을 우회합니다.
- root 제어 서비스의 Unix 소켓 권한, 모델 설정과 실행 파일의 ACL·심볼릭 링크, 잠금 파일의 생성·소유·교체 방지 방법.
- 서버 재부팅, Studio/gate 재시작 및 배포 중에도 잠금과 일시정지 상태를 안전하게 복구할 수 있는지.

## 안전한 조율 설계

Studio의 이미지 작업, client의 모델 전환, 운영자의 수동 전환은 같은 파일에 `flock` 배타 잠금을 사용합니다. 다른 소유자가 잠금을 잡고 있으면 이미지 작업은 실패하지 않고 대기하거나 재시도합니다. 전환은 잠금과 gate 일시정지를 확보하고, gate의 `active_requests`가 0이면서 llama 슬롯도 유휴인 것을 확인한 후 진행합니다.

잠금 파일을 사용 중에 삭제하거나 교체하면 서로 다른 파일을 잠글 수 있습니다. 현재 `/run/bc250-ai-studio`는 `ai-studio` 소유이므로 root 서비스가 이 경로의 심볼릭 링크나 바뀐 파일을 무조건 신뢰해서는 안 됩니다. 서비스 중지 시 디렉터리를 보존하는 설정만으로는 소유자의 고의적인 파일 교체를 막지 못합니다. root가 관리하는 디렉터리와 안전한 파일 권한 등으로 이 문제를 해결하고, 재부팅 시 디렉터리 생성 순서를 보장해야 합니다.

후보 경로는 `/run/bc250-gpu/gpu.lock`입니다. `systemd/bc250-gpu-lock.conf`는 root 소유 디렉터리와 root:ai-studio 소유 파일을 만들도록 준비한 설정이며 아직 설치하지 않았습니다. Studio의 `STUDIO_GPU_LOCK_SECURE_PRECREATED=true`는 미리 생성한 root 소유 파일만 열고 경로의 심볼릭 링크·쓰기 권한·파일 소유권을 검사합니다. Studio unit에 새 디렉터리 쓰기 예외도 준비했습니다. 운영 전환 시에는 **기존 경로와 새 경로를 동시에 사용하면 안 됩니다**. 모든 GPU 사용자와 직접 전환 경로를 중지하고, 설정·unit·권한을 함께 바꾼 후 같은 파일의 잠금을 사용하는지 확인해야 합니다. 전용 root 서비스와 이관 절차의 통합 검증이 끝날 때까지 새 설정을 활성화하지 않습니다.

gate는 일시정지 요청마다 소유자와 작업 ID가 있는 보관 상태를 유지해야 합니다. 어느 요청 하나라도 남아 있으면 gate는 닫혀 있고, 각 작업은 자기 요청만 해제합니다. 기존 `/control`의 불리언 요청은 별도의 기존 관리자용 상태만 바꾸도록 호환합니다. gate 재시작 시 상태가 사라져서는 안 되며, 상태를 읽을 수 없으면 닫힌 상태로 시작해야 합니다. 기존 Studio는 새 소유권 계약을 이해하지 못하므로 gate와 Studio를 유지보수 상태에서 함께 교체해야 합니다.

전환 작업은 잠금을 잡은 뒤 상태와 이전 모델을 기록하고 gate를 닫습니다. 요청을 비우고 고정된 권한 작업을 통해 모델을 변경한 다음 서비스 재시작과 health를 확인합니다. 실패하면 이전 설정을 복구하고 재시작과 health를 다시 확인합니다. 프로세스가 중간에 종료되거나 복구를 확인할 수 없으면 기록과 gate의 일시정지를 유지합니다. 재시작한 관리 서비스는 기록을 확인하고 같은 잠금을 잡아 복구해야 하며, 복구 전에는 새 GPU 작업을 막습니다. 단순 시간 만료로 gate를 자동 해제하지 않습니다.

현재 이 절차의 모의 구현은 실제 root 서비스와 연결되지 않았습니다. 특히 전환 프로세스가 종료되면 운영체제가 flock을 해제하므로, 기록이 남아 있는 동안 Studio를 포함한 모든 GPU 사용자가 작업을 거부하는 공통 차단 장치가 반드시 필요합니다. Studio 측에는 `STUDIO_SWITCH_JOURNAL_PATH`를 지정했을 때 공유 잠금 획득 후 root 소유 전환 기록을 확인하는 기초 코드를 추가했습니다. 파일이 없거나 손상돼도 작업을 시작하지 않습니다. 이 설정은 보안 잠금 설정도 필요하며 기본적으로 꺼져 있습니다. 기록 파일은 root가 관리하는 디렉터리에 사전 생성하고 Studio에 읽기 권한만 주어야 합니다. 다른 GPU 사용자와 root 서비스의 차단 장치는 아직 연결되지 않았으므로 잠금이나 gate hold만으로 이 조건이 충족된다고 가정하지 않습니다.

전환용 잠금·gate·systemd 어댑터 후보는 root 서비스에 연결하지 않았습니다. systemctl 재시작이 시간 초과되면 systemd 작업이 계속될 수 있으므로 결과 불명으로 기록과 gate hold를 유지하며, 복구 시 systemd 작업 종료를 확인한 뒤 이전 모델을 복원합니다. 프로세스가 종료되면 OS 잠금은 해제되므로 모든 GPU 사용자의 기록 차단 연동이 필요합니다. 후보는 root 소유 모델 설정의 제한된 리터럴 문법에서 예상 GGUF 경로를 읽어 `/v1/models`의 ID와 비교하고, 활성 설정 파일은 원자적으로 교체합니다. 따옴표·변수 치환 등 지원하지 않는 설정 문법은 실패 처리하므로 운영 모델 설정 전체의 호환성 확인이 필요합니다. 사용자가 제공한 정상 실행 상태에서 `systemctl show` 필드 형식과 현재 모델의 경로·ID 일치는 확인했지만 재시작·실패 중 출력과 다른 모델의 ID는 아직 확인하지 않았습니다.

권한 상승은 일반 sudo나 임의 셸 실행 대신 제한된 Unix 소켓을 가진 전용 root 서비스를 검토합니다. 이 서비스는 호출자와 허용된 모델 이름을 확인하고, 정해진 작업만 수행하며, 잠금과 gate 절차를 우회할 수 없어야 합니다. 모델 이름 검증만으로는 root가 `source`하는 설정 파일의 보안을 대신할 수 없습니다.

현재 준비된 코드는 systemd 소켓 활성화 방식으로 Unix 소켓의 커널 인증 UID를 확인하고, 제한된 크기의 모델 목록·현재 모델 요청만 처리합니다. 경로와 모델 설정의 소유자·쓰기 권한·심볼릭 링크를 확인하며 설정을 셸로 실행하지 않습니다. 읽기 전용 소켓·root 서비스 unit은 후보이며 아직 설치하지 않았고 전환 요청도 거절합니다. 설치 전에는 root 서비스가 실행하는 코드·가상환경과 모든 상위 디렉터리가 root 소유이고 일반 사용자가 수정할 수 없는지 확인해야 합니다. 이후 root 서비스는 자체적으로 GPU 잠금·gate·복구 절차를 강제해야 하며, 이 기초 코드만 서버에 설치해서는 안 됩니다.

## client가 사용할 API 제안

아래 API는 **분리된 테스트용 팩토리로 구현되었지만 운영 서비스에는 연결되지 않았습니다**. 자세한 요청·응답은 [모델 관리 API 후보](./LLM_MODEL_MANAGEMENT_API.md)를 참고합니다. client 백엔드만 별도의 모델 관리 권한을 가진 자격 증명을 사용합니다. 브라우저는 client 백엔드의 사용자 인증을 거치며 gate 키나 Studio 관리자 키를 받지 않습니다. 서로 다른 서버에 있다면 보호된 연결과 서비스 인증도 필요합니다.

요청 저장소 후보는 같은 인증 주체와 중복 방지 키의 재요청을 같은 작업으로 취급하고, 같은 키에 다른 모델을 지정하면 거절합니다. 하나의 GPU를 공유하므로 다른 작업이 진행 중이거나 복구가 필요한 동안에는 새 작업을 거절합니다. 작업자 후보는 설치 모델을 확인하고 요청 저장소와 전환 journal을 대조하지만, 인증 주체는 외부의 인증된 서비스가 제공해야 합니다. 작업자의 재시작 시 안전을 확인하기 전에는 작업을 완료로 표시하거나 새 전환을 허용해서는 안 됩니다. 작업자는 GPU 잠금과 다른 생명주기 잠금을 먼저 잡고 실행 중 요청이 끝나기 전에 그 잠금을 해제하지 않습니다. 실제 서비스에서 사용할 잠금 경로의 root 소유권과 권한을 아직 설정·검증하지 않았으므로 API나 root 서비스에 연결해서는 안 됩니다.

- `GET /api/v1/llm/models`: `{"models":[{"name":"example","current":true}],"current":"example"}`. `name`은 관리용 이름입니다.
- `POST /api/v1/llm/switches`: `{"model":"example"}`과 중복 방지 키를 받아 `202` 및 `{"id":"opaque-id","state":"queued"}`를 반환합니다. 경로, 명령, 서비스 이름은 입력받지 않습니다. 같은 키와 같은 요청은 같은 작업을 반환하고, 내용이 다르면 거절합니다.
- `GET /api/v1/llm/switches/{id}`: `queued`, `waiting_for_gpu`, `pausing`, `draining`, `switching`, `verifying`, `rolling_back`, `succeeded`, `failed_rolled_back`, `recovery_required` 중 하나와 시간·안전한 오류 코드를 반환합니다.
- 인증 실패는 `401`, 권한 부족은 `403`, 다른 전환 중이거나 복구가 필요하면 `409`, 모델 이름이 잘못되면 `422`를 제안합니다.

## 배포와 테스트 원칙

실제 스크립트·서비스·데이터를 백업하고 호출자와 이미지 작업을 중지한 유지보수 상태에서 호환되는 gate와 Studio를 함께 배포합니다. 잠금 경로와 상태 보관 권한을 검증한 뒤 전용 root 서비스와 client 접근을 차례로 활성화합니다. 롤백 시에도 gate를 닫고, 이전 gate가 새 소유권 상태를 보존하지 못한다는 점을 고려해 정상 복구 후 호환되는 구성 전체를 되돌려야 합니다. 구체적인 서버 명령은 실제 unit과 권한 확인 후 작성합니다.

출시 전 잠금 경합, 실행 중 요청 drain, 동시 전환, 이미지와 전환의 경쟁, gate 및 프로세스 재시작, 즉시 재시작 실패, health 시간 초과, 복구 성공과 실패, 인증과 모델 이름 검증을 단위·통합 테스트합니다. 운영 서버에서 모델 전환이나 GPU 작업을 자동으로 실행하지 않습니다.
