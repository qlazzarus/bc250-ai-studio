# 모델 관리 최초 이전 및 복원 설계

이 문서는 실행 승인된 운영 명령이 아닙니다. 개별 후보와 전체 절차를 Fedora 시험 VM에서 연결해 검증한 후 실행 명령을 확정합니다. 범위는 같은 서버의 관리 API이며 클라이언트 화면 변경과 운영 모델 전환은 포함하지 않습니다.

## 유지해야 할 상태

- Caddy의 `/api/*`와 `/llm/api/*`는 유지보수 중 503을 반환하고 `/wiki/*`는 계속 동작합니다. loopback 직접 호출자와 GPU 작업도 별도로 중단하고, 진행 중인 요청과 이미지 작업이 끝나야 합니다. Caddy 규칙만으로 로컬 호출자는 차단되지 않습니다.
- 기존 gate의 기존 관리자 pause는 유지보수 시작 전에 기록하며, 요청 중단과 이전 내내 기록을 보존합니다. 새 gate의 startup 및 legacy hold는 확인 없이 제거하지 않습니다.
- 전환은 비활성 상태로 설치합니다. 실제 모델 설정은 레이블 불일치가 확인된 상태이므로 변경하거나 정규화하지 않습니다.
- 백업은 root만 접근할 수 있어야 하며 비밀 파일을 포함합니다. 내용뿐 아니라 소유권, 모드, ACL, SELinux 문맥, 링크와 파일 시스템 경계를 고려해야 합니다. 데이터 일관성을 위해 Studio 종료 이후 백업합니다. 백업 완료 여부와 대상 목록을 별도로 기록하며 부분 백업으로 복원하지 않습니다.

## 단계와 통과 조건

1. **사전 점검:** 신규 대상이 없고, 후보 파일의 출처와 해시가 확인되고, 모델 설정이 지원되며, 여유 공간과 서비스 상태가 적합한지 검사합니다. 실패하면 운영 상태를 바꾸지 않습니다.
2. **유지보수 진입:** 현재 Caddy 설정을 보존하고 유지보수 후보를 검증한 다음 적용합니다. 두 API의 503과 Wiki 경로를 확인하고 직접 호출자·GPU 작업을 중단합니다. 실패 시 기존 설정을 복원하고 그 결과를 확인합니다.
3. **기존 gate 보호:** 기존 관리자 pause 값을 `capture`로 기록하고 gate를 pause합니다. 진행 중 요청이 0이 될 때까지 기다립니다. pause 결과가 불명확하면 기록을 보존하고 재조회합니다.
4. **서비스 정지와 백업:** Studio, LLM Client 및 기존 gate를 완전히 중지하고 프로세스와 systemd 작업 종료를 확인합니다. `/opt/bc250-ai-studio`, `/opt/ai-studio-data`, 기존 세 환경 파일과 unit, Caddy 설정 및 활성 모델 설정을 호환되는 복구 단위로 보존합니다. 변경 전 신규 경로 부재도 기록합니다. 완료 검증에 실패하면 유지보수를 해제하지 않습니다.
5. **신규 구성:** root 소유 코드·전용 키·빈 journal을 준비하고, 기존 pause 기록으로 gate 상태를 생성합니다. gate·Studio·Client drop-in, polkit, tmpfiles 및 신규 소켓·서비스를 설치하고 검증합니다. 중간 실패 시 기존 백업과 새 상태를 보존합니다.
6. **기능 검증:** 새 gate, Studio, 작업자 소켓, 관리 API와 Client를 시작합니다. gate hold, 활성 모델 health와 ID, Studio 조율, Client의 실제 프로세스 키와 관리자 역할, 관리 API의 인증·모델 목록 및 전환 비활성 응답을 확인합니다. `confirm-startup --expected-client-user yeppyshiba`는 검증이 통과한 경우에만 startup hold를 해제하며 기존 legacy hold는 보존합니다.
7. **유지보수 해제:** 확인된 기존 Caddy 설정을 복원하고 두 API 및 Wiki 동작을 확인합니다. 복원·검증 실패 시 유지보수 상태로 되돌리고 원인을 확인합니다.

## 복원 분기

- **새 코드가 아직 실행되지 않은 실패:** 서비스가 정지한 상태에서 완전한 백업을 확인하고 기존 코드·설정·unit과 데이터를 함께 복원합니다. 이전 gate를 시작한 뒤 기록한 관리자 pause 상태를 확인하고 기존 Client·Studio를 시작합니다. 모든 검증이 통과하기 전까지 유지보수를 유지합니다.
- **새 코드가 실행된 이후의 실패:** 새 gate 보류, journal, 작업 DB, Studio 복구 상태 및 진행 중 systemd 작업부터 확인합니다. 미완료 전환이나 불확실한 기록이 있으면 구 gate를 시작하거나 상태를 삭제하지 않습니다. 우선 검증된 복구 도구로 이전 모델과 health를 확인합니다. 자동 복구가 불가능하면 상태를 보존하고 중단합니다.
- 구 gate는 소유권 hold를 이해하지 않으므로 시작 직후 열린 상태가 될 수 있습니다. 외부와 로컬 호출자를 계속 차단한 상태에서 기존 관리자 pause를 명시적으로 복원하고 확인해야 합니다. 백업 이후 새 데이터가 생성됐을 가능성이 있다면 데이터 복원 전에 보존·검토합니다.
- Caddy와 기존 서비스·Client 인증, 기존 pause, 모델 health가 확인된 후에만 유지보수를 해제합니다. 새로운 경로와 비밀은 상태 확인 전에 삭제하지 않습니다.

## 전체 시험에서 필요한 증거

한 번의 격리 VM 실행에서 유지보수 진입, 기존 pause 보존, 일관된 백업, 모든 구성요소 설치, 인증 및 전환 비활성 확인, 유지보수 해제를 검증합니다. 별도 실행에서는 설치 중간과 새 서비스 시작 이후에 실패를 주입해 완전 백업의 복원, 기존 서비스와 키, pause 보존 및 유지보수 해제 조건을 확인합니다. 실제 운영 모델·GPU, 실사용자 데이터와 Caddy에는 이 시험을 적용하지 않습니다.

정지 후 백업을 위한 [후보 스크립트](../deploy/model-control/backup-stopped.sh)를 작성했습니다. 세 서비스의 완전한 정지, 보존된 Caddyfile과 기존 pause 기록을 요구하고, 코드·데이터·환경·unit·모델 설정을 ACL·확장 속성과 함께 아카이브합니다. 아직 시험 VM의 실제 systemd와 복원 시험을 통과하지 않았고 상위 경로 신뢰성, 백업 일관성, 복원과 전체 이전을 보장하지 않으므로 운영에 실행하지 않습니다.

아카이브 생성 부분을 [공통 함수](../deploy/model-control/backup-archive.sh)로 분리하고, 별도 시험 파일로 복원 내용과 소유권·권한·링크·확장 속성을 비교하는 [VM 시험](../scripts/test-backup-archive-vm.sh)을 준비했습니다. 이 시험은 별도 경로의 가짜 파일만 다루며 전체 서비스 이전 또는 복원을 대신하지 않습니다.

운영자가 해당 VM 시험을 실행해 내용, 소유권, 권한, 링크 및 기존 확장 속성의 복원을 확인했습니다. VM에 `setfacl`이 없어 추가 ACL은 확인하지 못했고, 가짜 파일 경로에 대한 SELinux 기본 레이블이 없다는 경고가 있었습니다. 운영 경로의 레이블 검증과 추가 ACL 시험은 별도로 필요합니다.

추가 시험에서는 가짜 파일에 POSIX ACL을 직접 생성하고 동일한 아카이브 함수로 저장·복원해 ACL 확장 속성이 일치함을 확인했습니다. SELinux 기본 레이블이 없는 가짜 경로에 대한 경고는 반복됐으므로 운영 경로에 대한 정책 확인을 대체하지 않습니다.

별도 VM의 실제 systemd 시험에서는 실행 중인 서비스와 `KillMode=process` 서비스를 백업 정지 조건에서 거절했고, 세 시험 서비스가 `control-group`으로 정지된 경우 통과했습니다. 전체 백업·배포·복원 절차를 연결해 시험한 결과는 아닙니다.

VM에서 이전 ACL 시험으로 만든 백업을 복사해 백업 디렉터리, 체크섬과 아카이브 목록 검증을 통과시켰습니다. 복사본의 Caddyfile을 변조하면 체크섬 검사에서 거절되는 것도 확인했습니다. 이 검사는 백업 당시 데이터의 일관성이나 서비스 복원 가능성을 증명하지 않습니다.

이어 VM의 가짜 백업을 별도 디렉터리에 복원해 아카이브 내용과 비교했고, 시험 파일의 추가 ACL 및 SELinux 속성 일치를 확인했습니다. 운영 서비스 경로를 교체하거나 서비스 재시작 및 기존 gate의 pause를 복원하는 시험은 아닙니다.

별도 VM의 레거시 호환 gate를 재시작한 뒤 기록된 기존 pause가 없던 경우와 있던 경우 모두 해당 상태를 복원했습니다. 그 과정에서 외부와 로컬 호출자를 차단하는 전체 유지보수 절차 및 구 서비스 전체 복원은 시험하지 않았습니다.

VM에서 레거시 gate pause 기록, 가짜 코드·데이터 백업, 소유권 gate의 startup·legacy 보류, 실패를 가정한 파일 복원, 구 gate 재시작 및 기존 pause 복원을 한 흐름으로 시험했습니다. 기존 pause가 있거나 없는 두 경우가 모두 통과했습니다. Studio·Client 서비스와 Caddy, 운영 경로 및 실제 GPU는 이 연결 시험에 포함되지 않았습니다.

별도 `bc250-llm-client` 저장소의 로컬 워크플로는 `main` push에서 해당 클라이언트 서비스를 배포·재시작하도록 작성돼 있습니다. 최초 이전 중에는 이 저장소 배포가 동시에 실행되지 않도록 운영자가 관리하고, 새 키 설정 적용 후 클라이언트를 수동으로 재시작할 수 있습니다. 확인한 로컬 배포 스크립트는 클라이언트 코드와 프런트엔드 교체 및 서비스 재시작을 수행하며 systemd drop-in을 수정하지 않습니다. 원격 워크플로와 운영 서버에 설치된 설정은 배포 시점에 확인해야 합니다.
