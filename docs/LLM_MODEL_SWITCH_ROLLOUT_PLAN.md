# 모델 관리 최초 이전 및 복원 설계

이 문서는 실행 승인된 운영 명령이 아닙니다. 개별 후보와 전체 절차를 Fedora 시험 VM에서 연결해 검증한 후 실행 명령을 확정합니다. 범위는 같은 서버의 관리 API이며 클라이언트 화면 변경과 운영 모델 전환은 포함하지 않습니다.

## 유지해야 할 상태

- Caddy의 `/api/*`와 `/llm/api/*`는 유지보수 중 503을 반환하고 `/wiki/*`는 계속 동작합니다. loopback 직접 호출자와 GPU 작업도 별도로 중단하고, 진행 중인 요청과 이미지 작업이 끝나야 합니다. Caddy 규칙만으로 로컬 호출자는 차단되지 않습니다.
- 운영자가 제공한 Wiki 코드에 따르면 Wiki 질문 기능은 gate를 거치지 않고 `127.0.0.1:8080`에 직접 요청합니다. Wiki API 변경은 이번 범위가 아닙니다. 단독 운영자는 유지보수 중 Wiki 질문과 다른 직접 GPU 호출을 사용하지 않고 기존 요청이 완료된 뒤 이전을 시작하며, 적용 직전 이를 확인합니다. 현재 유지보수 Caddy 후보는 Wiki 질문 요청을 자동으로 차단하지 않습니다.
- 기존 gate의 기존 관리자 pause는 유지보수 시작 전에 기록하며, 요청 중단과 이전 내내 기록을 보존합니다. 새 gate의 startup 및 legacy hold는 확인 없이 제거하지 않습니다.
- 전환은 비활성 상태로 설치합니다. 실제 모델 설정은 레이블 불일치가 확인된 상태이므로 변경하거나 정규화하지 않습니다.
- 백업은 root만 접근할 수 있어야 하며 비밀 파일을 포함합니다. 내용뿐 아니라 소유권, 모드, ACL, SELinux 문맥, 링크와 파일 시스템 경계를 고려해야 합니다. 데이터 일관성을 위해 Studio 종료 이후 백업합니다. 백업 완료 여부와 대상 목록을 별도로 기록하며 부분 백업으로 복원하지 않습니다.
- 보존된 Caddyfile은 원본의 소유권·모드·ACL·SELinux 속성을 유지한 채 root 전용 디렉터리에 보관합니다. 파일 자체를 강제로 0600으로 바꾸면 원본 권한을 복원할 수 없습니다. 후보 스크립트는 파일을 복사한 뒤 내용과 메타데이터·확장 속성을 비교합니다. Fedora 시험 VM의 0644 가짜 Caddyfile에 추가 ACL을 설정해 백업·격리 복원 후 내용, 권한, ACL 및 기존 확장 속성 일치를 확인했습니다. 운영 파일 복원 시험은 아닙니다.

## 단계와 통과 조건

1. **사전 점검:** 신규 대상이 없고, 후보 파일의 출처와 해시가 확인되고, 모델 설정이 지원되며, 여유 공간과 서비스 상태가 적합한지 검사합니다. 실패하면 운영 상태를 바꾸지 않습니다.
2. **유지보수 진입:** 현재 Caddy 설정을 보존하고 유지보수 후보를 검증한 다음 적용합니다. 두 API의 503과 Wiki 경로를 확인하고 직접 호출자·GPU 작업을 중단합니다. 실패 시 기존 설정을 복원하고 그 결과를 확인합니다.
3. **기존 gate 보호:** 기존 관리자 pause 값을 `capture`로 기록하고 gate를 pause합니다. 진행 중 요청이 0이 될 때까지 기다립니다. pause 결과가 불명확하면 기록을 보존하고 재조회합니다.
4. **서비스 정지와 백업:** Studio, LLM Client 및 기존 gate를 완전히 중지하고 프로세스와 systemd 작업 종료를 확인합니다. `/opt/bc250-ai-studio`, `/opt/ai-studio-data`, 기존 세 환경 파일과 unit, Caddy 설정 및 활성 모델 설정을 호환되는 복구 단위로 보존합니다. 변경 전 신규 경로 부재도 기록합니다. 완료 검증에 실패하면 유지보수를 해제하지 않습니다.
5. **신규 구성:** root 소유 코드·전용 키·빈 journal을 준비하고, 기존 pause 기록으로 gate 상태를 생성합니다. gate·Studio·Client drop-in, polkit, tmpfiles 및 신규 소켓·서비스를 설치하고 검증합니다. 중간 실패 시 기존 백업과 새 상태를 보존합니다.
6. **기능 검증:** 새 gate, Studio, 작업자 소켓, 관리 API와 Client를 시작합니다. gate hold, 활성 모델 health와 ID, Studio 조율, Client의 실제 프로세스 키와 관리자 역할, 관리 API의 인증·모델 목록 및 전환 비활성 응답을 확인합니다. `confirm-startup --expected-client-user yeppyshiba`는 검증이 통과한 경우에만 startup hold를 해제하며 기존 legacy hold는 보존합니다.
7. **유지보수 해제:** 확인된 기존 Caddy 설정을 복원하고 두 API 및 Wiki 동작을 확인합니다. 복원·검증 실패 시 유지보수 상태로 되돌리고 원인을 확인합니다.

## 복원 분기

- **새 코드가 아직 실행되지 않은 실패:** 서비스가 정지한 상태에서 완전한 백업을 확인하고 기존 코드·설정·unit과 데이터를 함께 복원합니다. 이전 gate를 시작한 뒤 기록한 관리자 pause 상태를 확인하고 기존 Client·Studio를 시작합니다. 모든 검증이 통과하기 전까지 유지보수를 유지합니다.
- **새 코드가 실행된 이후의 실패:** 새 gate 보류, journal, 작업 DB, Studio 복구 상태 및 진행 중 systemd 작업부터 확인합니다. 미완료 전환이나 불확실한 기록이 있으면 구 gate를 시작하거나 상태를 삭제하지 않습니다. 우선 검증된 복구 도구로 이전 모델과 health를 확인합니다. 자동 복구가 불가능하면 상태를 보존하고 중단합니다.
- 구 gate는 소유권 hold를 이해하지 않으므로 시작 직후 열린 상태가 될 수 있습니다. 외부와 로컬 호출자를 계속 차단한 상태에서 기존 관리자 pause를 명시적으로 복원하고 확인해야 합니다. 백업 이후 새 데이터가 생성됐을 가능성이 있다면 데이터 복원 전에 보존·검토합니다.
- 이전에 확인한 운영 Client 프로세스의 gate 키는 기존 gate 키와 달랐습니다. 따라서 롤백 후 기존 Client 키를 그대로 복원한 사실과 gate 관리자 인증 성공을 같은 것으로 취급하지 않습니다. Client는 운영자가 수동 재시작하고, 기존 설정·프로세스 상태와 가능한 인증 결과를 비밀값 없이 확인합니다. 기존에 없던 관리자 인증 성공을 롤백의 필수 조건으로 가정하지 않고, 확인된 기존 불일치는 결과에 명시합니다.
- Caddy와 기존 서비스·Client 인증, 기존 pause, 모델 health가 확인된 후에만 유지보수를 해제합니다. 새로운 경로와 비밀은 상태 확인 전에 삭제하지 않습니다.

## 전체 시험에서 필요한 증거

한 번의 격리 VM 실행에서 유지보수 진입, 기존 pause 보존, 일관된 백업, 모든 구성요소 설치, 인증 및 전환 비활성 확인, 유지보수 해제를 검증합니다. 별도 실행에서는 설치 중간과 새 서비스 시작 이후에 실패를 주입해 완전 백업의 복원, 기존 서비스와 키, pause 보존 및 유지보수 해제 조건을 확인합니다. 실제 운영 모델·GPU, 실사용자 데이터와 Caddy에는 이 시험을 적용하지 않습니다.

### 연결 구현의 중단 지점

다음 조건은 순서대로 모두 확인해야 하며 각 확인 전의 성공 메시지만으로 다음 단계에 들어가지 않습니다.

| 시점 | 계속하기 위한 확인 | 확인 실패 또는 결과 불명확 시 |
| --- | --- | --- |
| 유지보수 적용 | 실행 중 Caddy에서 두 API가 503이고 Wiki 조회가 동작함 | 서비스나 gate를 변경하지 않고 Caddy 실제 상태와 보관본을 확인합니다. reload 실패만으로 이전 설정이 적용 중이라고 가정하지 않습니다. |
| 기존 gate 일시 정지 | 기존 pause 기록이 안전하게 저장되고 gate 인증·pause·요청 drain이 확인됨 | 기록과 ingress 차단을 유지하고 gate 상태를 재조회합니다. |
| 세 서비스 정지·백업 | 세 서비스에 실행 프로세스와 진행 중인 systemd 작업이 없고, 백업과 검증이 완료됨 | 불완전한 백업을 복원에 쓰지 않고 서비스 상태와 기록을 보존합니다. |
| 새 서비스 시작 | 새 코드·설정이 함께 설치되고 gate hold와 빈 전환 상태가 확인됨 | 새 상태와 데이터의 사본을 보존하고 구버전과 혼용하지 않습니다. |
| Client 수동 재시작 | 운영자가 Client를 재시작한 뒤 실제 프로세스 키와 gate 관리자 역할이 확인됨 | startup hold와 유지보수를 유지합니다. |
| 유지보수 해제 | startup 확인, 기존 pause 보존 및 API·서비스 검증 완료 | 해제하지 않습니다. 해제 요청 결과가 불명확하면 실제 응답을 확인하고 상태를 보존합니다. |

새 코드가 실행된 뒤 복원할 때는 백업 이후 생성된 데이터와 journal·gate hold를 먼저 별도 보존하고, 미완료 전환이나 활성 모델 상태가 불명확하면 구 gate를 시작하지 않습니다. 구 gate 재시작은 외부 및 직접 호출을 계속 막은 상태에서 수행하고 저장된 관리자 pause 복원을 확인합니다. 이 표는 통합 실행기와 격리 시험의 요구 조건이며 운영 명령이 아닙니다.

## 통합 구현 전 확인 사항

- 백업 후보는 세 unit의 본문과 지정된 환경 파일, 존재하는 세 서비스의 `/etc/systemd/system` drop-in 디렉터리를 저장합니다. Fedora 시험 VM의 가짜 drop-in으로 내용·소유권·권한·확장 속성의 백업과 격리 복원을 확인했습니다. 운영 파일과 서비스 복원은 시험하지 않았습니다. Caddy의 별도 import 파일, 다른 위치의 systemd 설정 및 기타 서버별 의존성은 자동으로 수집하지 않습니다. 최초 이전 직전에 실제 유효 구성을 다시 확인하고, 필요한 파일을 복구 단위에 포함하기 전에는 이 백업을 전체 롤백용으로 간주하지 않습니다.
- drop-in이 외부 파일을 가리키는 경우 내용이 백업에서 누락될 수 있으므로 새 후보는 drop-in 내부 심볼릭 링크를 거절합니다. Fedora 시험 VM의 가짜 링크로 백업 파일 생성 전 거절과 링크가 들어간 아카이브의 복원 전 거절을 확인했습니다. 운영 설정에서는 배포 직전에 다시 확인해야 합니다.
- 유지보수 Caddyfile은 예시이며 Wiki의 주소와 기존 설정을 가정합니다. 실제 설정을 검토하고 동일한 경로 동작을 검증하기 전에는 그대로 적용하지 않습니다. 별도 로컬 호출자와 직접 GPU 사용자의 중단도 필요합니다.
- 운영자가 제공한 Caddyfile에는 import가 없고 Wiki는 `127.0.0.1:8020`입니다. [유지보수 후보 생성기](../deploy/model-control/create-maintenance-caddy.py)는 이 정확한 지시문 구성을 확인한 뒤 두 API 블록만 바꾸며, 변경된 구성이나 import를 만나면 중단합니다. 운영자가 운영 서버의 실제 Caddy 실행 파일로 후보 문법을 확인하고 별도 loopback 포트에서 두 API의 503과 Wiki·정적 경로를 시험했습니다. 실행 중인 Caddy에는 적용하지 않았습니다. 유지보수 진입·원본 복원 및 전체 서비스 연동 시험은 아직 남았고, 배포 직전 원본도 다시 확인해야 합니다.
- [Caddy 보관 후보](../deploy/model-control/capture-caddy.py)는 기존 설정을 적용하기 전에 root 전용 디렉터리에 원본과 유지보수 후보를 따로 저장합니다. 원본의 내용·소유권·모드·확장 속성 및 보관 중 변경 여부를 검사하며 Caddy를 reload하지 않습니다. Fedora 시험 VM에서 추가 ACL이 있는 가짜 원본의 보관과 예상 밖 설정의 거절을 확인했습니다. 운영 절차 연결은 아직 남았습니다.
- 같은 보관 후보의 검증 기능은 Fedora 시험 VM에서 기존 가짜 자료의 복사본을 사용해 정상 일치, 유지보수 후보 변조 및 현재 원본 변경을 확인했습니다. [파일 교체 후보](../deploy/model-control/caddy-file-swap.py)는 내용과 보호 속성을 검사한 뒤 원자적으로 파일을 교체하는 내부 함수이며 reload나 실행 CLI가 없습니다. Fedora 시험 VM의 가짜 파일에서 교체·복원과 교체 직전 실패 시 원본·임시 증거 보존을 확인했습니다.
- 운영 서버의 별도 loopback 포트에 실행한 시험 Caddy와 가짜 백엔드에서 시험 파일 교체와 reload를 연결했습니다. 잘못된 설정으로 reload가 실패하자 기존 API·Wiki 응답이 유지됐고, 시험 파일을 복원한 후 정상 reload와 유지보수 진입·원본 복원을 확인했습니다. 이 실패는 잘못된 설정의 거절을 확인한 것이며 reload 통신 단절이나 적용 결과가 불명확한 경우를 증명하지 않습니다. 시험에서는 임시 경로의 root 소유권 검사를 대체했습니다. 운영 Caddy reload 및 실제 서비스의 중단·복원은 포함되지 않습니다.
- reload 결과가 불명확하면 파일 내용만으로 실제 적용 상태를 판단하지 않습니다. 외부 및 직접 호출 차단을 확인할 때까지 서비스 이전을 시작하지 않고, 실행 중인 Caddy의 실제 응답과 설정을 확인할 수 없으면 상태와 증거를 보존하고 중단합니다.
