# LLM Client 모델 전환 현황과 재정렬 제안

> **2026-11-07 문서 정리:** 이 문서는 이전 설계·조사·시험 기록입니다. 현재 목표와 후속 작업은 [모델 전환 문서 안내](LLM_MODEL_SWITCH.md)를 통해 **bc250-llm-client의 통합 계획**을 따릅니다. 본문의 API 전용 범위·Client 제외·T1~T6 및 DB 차단 우선순위는 현재 작업 지시가 아닙니다. 과거 증거와 구현 제약은 보존하며, 운영 상태·최종 검증 완료를 뜻하지 않습니다.

검토일: 2026-11-07. 두 로컬 저장소의 문서, 코드, Git 기록 및 미커밋 변경을 읽어 확인했다. 서버에 접속하거나 테스트·배포·모델 전환을 실행하지 않았다. 기존 문서의 운영 및 VM 시험 결과는 기록으로만 확인했으며 현재 서버 상태나 최종 작업 트리의 통과 결과로 보증하지 않는다. 이 문서는 다음 구현 전 검토안이며 기존 운영 절차를 대체하지 않는다.

## 목표와 판정

이번 사용자 요청을 기준으로 목표는 **bc250-llm-client 화면에서 설치된 LLM을 선택하고, BC-250의 활성 LLM을 실제로 전환한 뒤 대화를 계속하는 것**이다. 후속 사용자 설명으로 대상은 llama-server이며, 기존 서버 콘솔에서는 `ai-model` 명령을 사용했음이 명확해졌다. UI와 서비스 전환 API의 구현·배포 주체는 bc250-llm-client다. imagegen은 stable-diffusion 기반 이미지 Studio이며 이 기능의 주 프로젝트가 아니다.

목표 제어 경로는 **Client UI → Client 백엔드 API → 제한된 서버 제어 실행부 → 기존 ai-model → llama-server**다. 기존 명령의 실제 코드·입출력·권한·실패 동작을 확인한 후 어댑터를 설계한다. 기존 imagegen 후보는 ai-model을 직접 호출하지 않고 활성 설정을 변경하는 방식도 포함하므로 그대로 채택하지 않는다. 별도 8091 API나 imagegen 전체 이전은 필수 구조로 전제하지 않는다.

현재는 이 목표가 충족되지 않았다. 기반 구현은 재사용할 수 있지만 기존 배포 계획을 전부 완료해도 Client UI와 실제 전환 활성화가 범위 밖이므로 사용자 목표가 자동으로 완성되지 않는다.

## 왜 시험을 계속해도 목표에 가까워지지 않는가

단순히 같은 테스트가 실패해서 반복되는 상황이라고 단정할 수는 없다. 기록에는 서로 다른 시험의 성공과 실제 결함 발견이 있다. 다만 제품 목표와 시험 완료 기준이 분리됐다.

1. Client 모델 전환이 서버 관리 API 배포 프로젝트로 바뀌었다.
2. API 배포가 Studio·gate·Wiki·Client의 전체 이전 및 복구 조율에 의존한다.
3. 전체 이전은 서비스 밖 DB 쓰기와 기존 FD까지 지속 차단하는 조건에 걸렸다.
4. 개별 차단 기법의 한계가 발견될 때마다 새로운 VM 시험과 대안 설계가 추가됐다.
5. Client 화면과 실제 전환은 제외돼 있어 부분 시험 성공이 사용자 기능 완성으로 이어지지 않는다.

TASKS의 18/36, 50%는 배포 체크리스트 수치이며 사용자 기능 완성률이 아니다. 최신 문서 자체도 T2의 직접 호출·DB 쓰기·신규 작업 차단 완료 조건을 0/3으로 기록한다. 기존 DB 차단 조건을 충족했다고 간주하거나 콜백을 무조건 성공으로 바꾸는 해결은 적절하지 않다. 배포 범위와 신뢰 경계를 먼저 재설계해야 한다.

## 재사용할 것과 분리할 것

- 유지: 단일 전환 작업자, 설치 모델 검증, 요청 중복 방지, GPU 공유 잠금, gate 요청 배출, 이전 모델 복구, 복구 불명 상태 차단, 제한된 root 작업 경계.
- Client에 추가: 관리자 권한 검사, 내부 관리 API 어댑터, 설치 모델 목록과 선택 UI, 진행·실패 표시, 새로고침 후 작업 추적, 전환 후 모델 정보 갱신.
- 별도 후속 과제로 분리 검토: 통합 Actions 자동 배포, 범용 배포 재진입, 유지보수 부팅, 임의 프로세스의 DB 접근을 포괄하는 격리 연구. 최초 수동 배포가 이 기능들에 의존하지 않는지 검토한 뒤 분리한다.
- 후속 구현과 계획의 주 저장소는 llm-client다. imagegen 후보는 참고 자료로 보존하고 필요한 전환·복구 로직만 검토해 Client 측 실행부에 재사용한다. 기존 gate·이미지 작업과의 GPU 조율은 필요한 연동 범위만 다룬다. imagegen DB 이전이나 전체 배포 체계를 이 기능의 선행 조건으로 삼지 않는다.

## 사용자 설명 반영: 다음 작업의 우선순위

아래 순서가 앞선 전체 배포 중심 계획보다 우선한다. 현재는 현황·계획 정리 단계이며 기능 구현이나 서버 변경을 시작하지 않는다.

1. 실제 `/opt/ai/scripts/ai-model`과 llama-server unit을 읽기 전용으로 확인한다. 로컬의 `deploy/ai-model-recovery-candidate`는 운영 원본으로 간주하지 않는다. `list`, `status`, `switch`의 출력·종료 코드·권한·재시작·복구 동작을 확인한다.
2. llm-client에서 설치 모델 목록, 현재 모델, 전환 요청, 전환 상태 조회 API와 UI를 설계한다. 명령은 서버에서 고정된 실행 파일과 검증한 모델 인자로 호출하며 브라우저나 입력 문자열을 셸 명령으로 전달하지 않는다. 웹 백엔드 전체를 root로 실행하지 않는다.
3. Client의 채팅·요약·이미지 프롬프트 요청을 전환 중 대기 또는 제한하는 방식을 정한다. 이미 실행 중인 요청을 배출하고 중복 전환을 막는다. 이미지 GPU 작업과 다른 llama 호출자는 별도 연동 조건으로 확인한다.
4. 가짜 명령 실행부로 Client UI→API→전환 작업→상태 갱신을 먼저 완성한다. 실제 ai-model 연결 후에는 명령 성공뿐 아니라 llama health·실제 모델 ID와 전환 후 대화까지 확인한다.
5. 기존 ai-model의 복구가 부족하면 Client 측 제한된 실행부 또는 공용 명령 계층에서 보완한다. 수동 콘솔 전환과 UI 전환은 같은 활성 설정을 사용하고 상태가 일치해야 한다.
6. 관련 기능 시험과 필요한 수동 배포·복구 절차만 준비한다. 기존 imagegen T1~T6를 완료하는 작업은 이 계획의 기본 경로에서 제외한다.

## Client 연결 전에 해결할 구체적인 문제

1. 관리용 모델 이름과 추론 API의 GGUF ID가 다르다. 설치 목록과 현재 모델 ID를 구분한다.
2. Client의 `LLM_MODEL_ID`가 고정돼 있으면 전환 후 `configured_model_unavailable`이 발생할 수 있다. 현재 활성 모델 추종 정책과 설정 이전을 설계한다.
3. Client는 단일 전역 `llm_context_tokens`를 사용한다. 모델별 컨텍스트 한도·추론 옵션 호환성을 확인하고 필요한 메타데이터 또는 보수적인 공통 설정을 정한다.
4. Client의 현 인증은 local 모드 또는 공용 API 키다. 관리자와 일반 사용자를 구별하는 권한 검사는 별도로 필요하며 local 접근 검사만으로 관리자 권한을 부여하지 않는다.
5. 문서에는 Client/gate 키 불일치와 Wiki의 llama 직접 호출이 기록돼 있다. 현재 상태를 재확인하고 전환 중 모든 실제 추론 호출자의 조율 방식을 확정한다. Wiki 수정이나 정지가 필요하면 별도 의존 작업으로 명시한다.
6. 모델 조회와 추론 제출 사이 전환 경합, 진행 중 채팅·요약·이미지 프롬프트 요청의 대기·실패 동작을 함께 정의한다. 이미 생성한 응답이나 이미지 작업을 무조건 자동 재제출하지 않는다.

## 다음 실행 계획과 완료 조건

| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| 1. 목표 고정 | Client에서 서버 활성 모델 전환을 최종 목표로 복원하고 기존 API 전용 범위와 구분. 미커밋 후보 보존 | 하나의 기능 체크리스트에 UI·API·실제 전환·후속 대화가 모두 포함됨 |
| 2. 최초 배포 범위 재설계 | 실제 서비스/호출자/DB writer를 목록화하고 허용 가능한 유지보수 중지 및 수동 복구 절차를 정의. 공유 잠금·gate 이전 요구는 유지 | 무엇을 멈추고 백업·교체·복구하는지 구체적이며 미구현 범용 차단기에 의존하지 않는 실행안. 불가능하면 정확한 차단 요인을 기록하고 설계를 재검토 |
| 3. Client 기능 구현 | 관리자 API 어댑터와 모델 선택·진행 UI. 먼저 가짜 관리 서비스로 전체 사용자 흐름 연결 | 선택 → 접수 → 상태 조회 → 성공/복구 실패 표시와 권한 거절을 Client에서 확인 |
| 4. 서버 후보 연결 | 기존 작업자와 gate/Studio 조율을 연결하고 모델 ID·키·컨텍스트 정책 반영 | 격리 환경에서 같은 Client 경로로 모델 A→B 및 후속 대화까지 성공 |
| 5. 필요한 통합 검증 | 정상 전환, GPU/채팅 대기, 중복 요청, 실패 후 복구, 중단 후 상태 유지·복구, 권한 차단 | 최종 후보 기준 각 수용 조건의 증거 확보. 가짜 모델 시험과 실제 GPU 시험을 구분 |
| 6. 운영 적용 준비 | 검증된 수동 설치·롤백 절차와 현재 서버 사전 점검 결과 정리 | 검토 가능한 최종 변경·명령·복구 방법 준비. 운영 적용은 별도 단계 |
| 7. 운영 기능 확인 | 배포 후 사용자와 실제 모델 전환 및 대화 확인 | Client에서 설치 모델 선택 → 실제 활성 모델 변경 → 다음 대화 성공. 실패 시 복구 상태도 명확히 표시 |

3단계는 서버 배포 연구의 완료를 기다리지 않고 진행할 수 있다. 운영 활성화는 2·4·5·6단계가 충족된 뒤 진행한다. 이 검토에서는 어느 구현 단계도 시작하지 않았다.

시험은 수용 조건과 연결된 것만 실행한다. 통과한 시험은 관련 코드 변경·실패·최종 연결의 필요가 있을 때 재실행한다. 새로운 하위 시험은 해결할 구체적 결함과 완료 조건을 먼저 적는다. 설계 자체가 막히면 미세 시험을 계속 추가하지 않고 범위와 운영 전제를 다시 검토한다.
