# 모델 관리 API 운영 배포까지 남은 작업

기준: 2026-11-03 작업 트리와 운영자가 전달한 시험 결과. 현재 **운영 배포 준비가 완료되지 않았다.** 이 문서는 작업 목록이며 운영 실행 명령이 아니다. LLM Client 화면의 모델 선택과 실제 모델 전환은 이번 범위 밖이다.

현재 운영 서비스와 추가 예정 구성은 [BC-250 서비스 구성](./BC250_SERVICE_INVENTORY.md)에서 별도로 관리한다.

## 현재 진행률과 배포까지 남은 범위

기준: 2026-11-05, 운영자가 전달한 마지막 시험 결과까지. **중간 점검 항목은 36개 중 18개 완료, 체크리스트 진행률 50%다.** T1~T6의 중간 항목을 한 개씩 같은 비중으로 계산한 값이며, 실제 작업량·남은 시간·운영 배포 준비도의 정밀한 측정은 아니다. 최종 변경을 반영하지 않은 과거 시험은 아래에 **기준 시험**으로 구분했으며 최종 회귀 완료로 취급하지 않는다. 범위가 바뀌어 항목이 추가되면 분모와 퍼센트도 다시 계산한다.

별도로 **전체 완료 기준을 충족한 시험 묶음은 6개 중 T1 하나, 약 17%**다. 이는 아래 부분 진행률과 다른 지표이며, 나머지 묶음에도 완료된 중간 항목이 있다.

### T1~T6 중간 진행률

각 체크 표시는 명시된 범위의 증거가 있다는 뜻이다. 모의 조건을 포함한 중간 시험의 통과는 운영 전체 검증의 완료를 뜻하지 않는다. 합계는 각 묶음의 백분율을 평균하지 않고 **완료 항목 수 ÷ 전체 항목 수**로 계산한다.

| 묶음 | 완료/전체 | 진행률 | 남은 전체 완료 조건 |
| --- | ---: | ---: | --- |
| T1 Caddy·복원 연결 | 4/4 | 100% | 이 묶음의 시험 기준 충족. 모델 health·로컬 유휴 등 모의 조건은 T2·T3에서 별도 확인. |
| T2 정상 전체 배포 | 3/7 | 약 43% | 지속 차단·GPU 검사, 실제 조율기와 전체 정상 흐름 완성. |
| T3 실패 복구 | 3/7 | 약 43% | 부분 설치·신규 기동 실패를 실제 복원 흐름에 연결. |
| T4 중단·재진입 | 4/8 | 50% | 기록 기반 소유권·재진입과 종료·재부팅 전체 연결. |
| T5 최종 검증 | 2/5 | 40% | 최종 커밋 기준 회귀·lint·빌드·아티팩트 검증. |
| T6 Actions 배포 | 2/5 | 40% | 실제 출처 인증·SSH 통합 경계 및 격리 대상 실행 검증. |
| **합계** | **18/36** | **50%** | 위 미완료 항목과 아래 운영 직전·배포 후 확인 필요. |

실제 운영 배포를 위해서는 위 작업 외에 운영 직전 gate pause·요청 수, 모델 health, 디스크·계정·권한·SELinux와 최종 설정을 다시 확인하고, 운영자가 Client를 수동 재시작한 뒤 관리 API와 기존 서비스 응답을 검증해야 한다. 운영 모델 전환은 별도 작업이다. 배포 기록 릴리스 식별 비교 VM 부분 시험은 통과했지만 실제 Actions 출처 인증은 아직 미완성이므로 묶음 완료율에는 변화가 없다.

### 앞으로 실행할 검증 목록

아래는 **현재 설계에서 계획한 배포 전 7개 검증 항목**이다. 명령 실행 횟수가 아니라 확인해야 하는 시나리오 수이며, 미구현 기능을 먼저 완성해야 실행할 수 있다. 오류가 발견되거나 구현이 바뀌면 관련 범위의 재시험이 추가될 수 있다. 이미 통과한 개별 시험은 변경·연결 검증에 필요한 경우 외에는 반복하지 않는다.

| 순서 | 상태 | 남은 검증과 완료 조건 | 선행 작업 |
| --- | --- | --- | --- |
| 1 | 준비 필요 | **정상 전체 흐름**: Fedora VM에서 시험 릴리스·설정 준비 → Caddy 유지보수 → Wiki 및 다른 직접 호출자 차단 → gate pause·drain → Studio 정지·DB 검사·백업 → 모델 제어·Studio 설치 → 신규 서비스 기동 → Client 수동 재시작 → 인증·전환 비활성 확인 → 이전 pause 보존과 유지보수 해제까지 연결한다. | 실제 직접 호출자 차단·GPU 안전 및 잠금 인계 검사기와 실행 조율기 완성. |

## 이전 시험 경과

아래는 진행 당시의 기록이다. 당시의 “필요”, “아직 없다” 등의 표현은 현재 상태를 뜻하지 않으며, 현재 상태는 위 표를 따른다.

- Fedora 격리 VM에서 유지보수용 Caddy의 실제 systemd reload, 시험 gate pause·drain, 가짜 백업과 기존 구성 복원 흐름을 연결해 확인했다. 일부 데이터·로컬 유휴·모델 health는 모의였다.
- 시험 서비스에서 관리 API 인증, 가짜 모델 목록, 전환 비활성, Client 키 전달, startup 해제와 기존 보류 보존을 확인했다. 실제 운영 GPU와 전체 운영 서비스의 통합 시험은 아니다.
- 시험 경로에서 모델 제어와 Studio 코드를 별도 캐시로 설치하고 가짜 백업·pause 이관·unit 설치를 연결했다. 릴리스·설정·유지보수·로컬 유휴 검사는 모의였다.
- 가짜 아티팩트에서 릴리스 검증, 초기 설정과 빈 journal 생성, 시작·완료 기록, 완료된 준비 기록 확인 후 조율기 조립을 확인했다. 실제 GitHub Actions 출처를 인증한 결과는 아니다.
- 운영자가 Studio 모델 설정과 당시 로컬 작업 트리 후보의 내용이 일치함을 읽기 전용으로 확인했다. 최종 아티팩트와 배포 직전 파일은 다시 검사해야 한다.
- 서로 다른 시험 Studio 모델 설정을 설치 전에 거절하고 원본을 보존하는 VM 시험이 통과했다.
- 시험 Wiki unit의 정지·cgroup과 가짜 llama 슬롯 상태를 확인하는 관찰이 VM에서 통과했다. 다른 직접 호출의 지속 차단을 검증한 것은 아니다.
- 시험 Studio의 인증된 상태·작업 관찰과 대기 작업·복구 필요·인증 실패 거절이 VM에서 통과했다. 이후 요청을 차단하는 시험은 아니다.
- 정지된 시험 Studio의 DB·WAL 사본 검사, WAL에 있는 대기 작업 거절과 원본 보존이 VM에서 통과했다. 직접 DB 쓰기 차단은 시험 범위 밖이었다.
- 시험 Studio 정지 후 DB 검사와 백업 어댑터의 연결, 대기 작업이 있을 때 백업 전 중단이 VM에서 통과했다. gate·유지보수·백업 파일 생성은 모의였다.
- 운영자가 실행 중인 Studio의 데이터 경로와 백업 검사 후보의 DB 파일 위치가 일치함을 읽기 전용으로 확인했다. 배포 직전에 다시 확인해야 한다.
- Wiki runtime mask 시험은 실패했다. `/etc/systemd/system`의 시험 unit이 `/run`의 mask보다 우선해 재시작됐으며 시험 unit과 증거는 보존 중이다. 운영 Wiki도 `/etc` unit이므로 이 방식은 사용할 수 없다.
- 후속 시험에서 `/etc` unit에 runtime mask를 적용하기 전에 거절하고 시험 서비스가 그대로 실행 중인 것을 확인했다. 별도 VM의 가짜 `/etc` unit에서는 runtime 조건이 수동 시작과 의존 unit의 시작 요청을 막았고 조건 해제 후 다시 시작됐다. 운영 후보는 아직 없으며 조건의 실제 로드·유지와 기존 drop-in과의 충돌을 검증해야 한다.
- 저장된 시험의 `systemctl show`에서 조건 자체는 `[unprintable]`이었다. 조건 적용을 단순 문자열로 판정하지 않으며, systemd D-Bus의 구조화된 속성을 별도 가짜 unit에서 확인해야 한다.
- D-Bus 진단에서 비활성 시험 unit이 `GetUnit` 조회 시 로드되어 있지 않아 중단됐다. 실패 기록은 보존했고 새 가짜 unit을 실행해 객체를 유지하면서 조회하도록 시험을 수정했다.
- 실행 중인 가짜 unit에서 D-Bus 조건의 구조화된 형식과 부정 조건을 확인했다. 정지된 unit을 동일 연결에서 로드·참조하며 조회하는 후보와 값 검증기를 추가했으며 별도 VM 확인이 필요하다.
- 정지된 시험 unit에서도 같은 D-Bus 연결로 정확한 부정 경로 조건을 조회·검증했다. 이를 이용한 Wiki 조건 차단 후보의 systemd·SELinux 시험과 전체 배포 연결은 남았다.
- runtime 조건을 이용한 시험 Wiki의 systemd 시작 차단과 이전 실행·정지 상태 복원이 VM에서 통과했다. runtime 조건은 재부팅하면 사라진다. 별도의 영구 조건 후보는 systemd 재실행과 실제 VM 재부팅 검증이 필요하다.
- 영구 조건 후보는 VM의 systemd 재실행 후에도 시험 unit의 정지 상태가 유지됐고 이전 실행·정지 상태 복원이 통과했다. 실제 재부팅 후에는 프로세스가 사라지므로 완료 기록을 확인해 이어가는 후보와 2단계 VM 시험을 준비했다. 아직 재부팅 결과는 없다.
- 2단계 재부팅 시험의 준비 단계에서 가짜 unit 자동 시작 설정, 영구 조건과 정지 상태 및 차단 기록을 확인했다. 시험 VM 재부팅과 재부팅 후 검증은 아직 수행하지 않았다.
- 실제 시험 VM 재부팅 후 가짜 Wiki unit의 자동 시작 차단과 완료 기록을 확인하고, 기록 기반 차단 해제 및 이전 실행 상태 복원이 통과했다. 다른 직접 호출의 차단은 시험하지 않았다.
- 조율 후보와 영구 Wiki 차단을 연결한 시험에서 Client 수동 대기 동안 차단 유지, 완료 후 기존 상태 복원과 설치 실패 시 차단·미완료 기록 보존을 확인했다. Caddy·gate·백업·설치·Client는 모의였다.
- 수동 Client 재시작 경계를 포함한 롤백 순서 후보와 관련 기록을 추가하고 로컬 시험을 통과했다. Fedora VM에서 Wiki 차단과 수동 재시작 경계 및 안전하지 않은 보존 상태의 거절을 확인했다. gate·Studio·Client·데이터·Caddy는 모의였다. 별도 VM 연결 시험에서 실제 시험 Caddy 유지보수 중 시험 gate·서비스 정지·백업 검증·파일 복원과 Client 수동 재시작을 확인했다. 이 연결 시험에서 Wiki 차단·모델 health·로컬 유휴와 후보 내부의 유지보수 해제는 모의였으며 운영 진입점은 남았다.
- 최근 전달된 Fedora 컨테이너 결과는 백엔드 284개 통과, 6개 건너뜀과 Ruff 통과다. 이는 이후 변경을 포함한 최종 커밋의 시험 결과가 아니다. 완료된 개별 시험을 일괄 반복하지 않고 변경된 범위와 최종 결과를 확인한다.

## GPU 잠금 이전 시 확인된 제약

- 운영 Studio의 설치 소스는 작업 시점에 잠금 파일을 생성할 수 있다. 현재 명시된 기존 경로의 파일이 없고 상위 경로도 새 협조 잠금 후보의 신뢰 조건을 만족하지 않았다. 이 관찰은 GPU 유휴나 다른 작업의 부재를 증명하지 않는다.
- 기존 경로에 파일을 임의로 만들거나 소유권·권한을 변경해 시험 후보를 적용하지 않는다. 기존 Studio 정지 및 작업 DB 검사, gate·Wiki 격리와 다른 직접 호출자 조건을 먼저 확정해야 한다.
- 신규 구성의 `/run/bc250-gpu/gpu.lock`은 설치 과정의 tmpfiles 후보로 준비된다. 새 잠금이 기존 잠금과 같은 inode라고 가정하지 않는다. 새 잠금 보유만으로 이전 경로의 참여자, llama 직접 요청 또는 GPU 장치 전체가 차단되지는 않는다.
- 실제 절차에 협조 잠금을 연결하기 전에 기존·신규 서비스가 각각 어느 시점에 어떤 inode를 사용하는지, 잠금 보유 중 시작이 교착하지 않는지, 중단·재부팅 후 gate와 Wiki 차단이 유지되는지 검증해야 한다. 이 조건과 직접 호출자 지속 차단은 아직 구현·운영 검증되지 않았다.
- 현재 `NewServiceStart.start()`는 로컬 유휴 조건을 확인한 뒤 `systemd-tmpfiles`로 신규 잠금 파일을 만든다. 이어지는 `confirm-startup`도 같은 잠금을 직접 획득한다. 별도의 인계 순서 후보를 추가했으나 실제 시작 어댑터에 연결하지 않았다. 유휴 검사에서 미리 신규 잠금의 보유를 요구하면 파일 생성 전에 막히므로, 운영 연결 전에 준비 순서와 단계별 검사 계약을 바꿔야 한다.
- 기존·신규 Studio는 같은 systemd unit 이름을 쓴다. 신규 서비스 시작 후에도 기존 프로세스 세대가 종료됐는지 확인해야 하며, unit 전체가 계속 정지 상태라고 요구하는 검사로 대체하면 정상 기동과 충돌한다. PID 재사용과 남은 cgroup 프로세스를 포함한 구별 방법은 아직 미구현이다.
- 협조 `flock`은 프로세스 종료 시 해제되므로 종료·SSH 유실 이후에도 잠금이 유지된다고 가정하지 않는다. 재진입은 별도의 gate·Wiki 차단과 작업 기록 검증 후에만 판단한다.
- 현재 조율기와 시작 잠금 후보의 단계는 프로세스 메모리에 있다. 수동 Client 재시작을 기다리는 동안 동일 프로세스가 잠금을 보유해야 하며 SSH 종료 후의 잠금 유지나 단계 재개는 구현되지 않았다. 수동 경계의 프로세스 수명과 실패 시 기록 기반 진단·차단 절차를 설계하기 전에는 두 후보를 운영 경로에 연결하지 않는다.
- `confirm-startup` 응답 유실은 gate에서 startup 보류 해제가 이미 적용됐을 가능성을 포함한다. 별도 관리자 보류가 남아 있지 않은 경우 gate가 재개될 수 있으므로, 미완료 기록이나 Wiki 차단만으로 gate 차단이 유지된다고 판단하지 않는다. 자동 재시도 없이 인증된 상태를 확인하고 차단을 다시 확보하는 절차 및 그 실패 시험이 필요하다.

## 배포 전 필수 작업

- [ ] **실행 가능한 전체 조율기 완성:** 인증된 아티팩트 준비, 초기 설정, Caddy 유지보수, gate pause 기록·drain, 서비스 정지, 일관된 백업, 모델 제어·Studio·unit 설치, 신규 서비스 시작을 연결한다. Wiki 영구 조건을 조율 후보에 연결한 VM 시험은 통과했으며 다른 핵심 구성요소의 연결이 남았다. 현재 내부 조율 후보는 운영 CLI가 아니며 필수 검증 콜백이 남아 있다.
- [ ] **실제 유휴·안전 검사 구현:** Studio 작업과 복구, gate 대기·진행 요청, llama 및 직접 호출자, GPU 잠금과 systemd 상태를 실제 환경에서 확인한다. Wiki·llama와 Studio의 순간 관찰 및 정지된 Studio의 DB 검사를 백업 어댑터와 연결한 시험이 VM에서 통과했다. 실행 중 운영 Studio의 DB 경로도 한 차례 확인했다. Wiki runtime mask는 `/etc` unit을 차단하지 못해 실패했으며, 이를 사용하지 않는 직접 호출·DB 쓰기 및 신규 작업의 지속 차단이 필요하다. 관찰 성공만으로 배포를 허용하지 않는다. Wiki 기능 변경은 범위 밖이다.
- [ ] **운영 사전 준비 확정:** `ai-gate` 계정과 경로·소유권·ACL·SELinux·디스크 공간·포트·uv 및 Python 의존성을 확인하고, 신규 상태·설정·코드가 기존 항목과 충돌하지 않는지 검사한다. Client·gate·Studio 환경의 키 값은 출력하지 않는다.
- [ ] **릴리스와 운영 설정의 호환성 확인:** 운영 중인 모델 설정 및 GGUF, 현재 모델과 health를 비교한다. Studio 설치 후보가 릴리스의 `config/models.yaml`을 설치하므로 서버 설정과 차이를 검토하고 유지할 내용을 결정한다. [읽기 전용 비교 스크립트](../scripts/compare-studio-model-config-remote.sh)로 한 차례 일치를 확인했으며, 설치 후보에 불일치 중단 검사를 추가했다. 설정 불일치 거절의 Fedora VM 시험은 통과했다. 최종 Actions 아티팩트 및 배포 직전 파일의 확인은 남았다. `/opt/ai/config/active-model.conf`는 임의로 수정하지 않는다. 전환은 비활성으로 유지한다.
- [ ] **수동 Client 재시작 경계 완성:** 사용자에게 새 gate 키 적용 후 Client 수동 재시작을 안내하고, 실행 중 프로세스의 키·서비스·gate 인증을 확인한 뒤 startup hold만 해제한다. 기존 관리자 hold는 보존한다. 프로세스 종료나 SSH 연결 유실 시 안전하게 중단하고 확인할 수 있어야 한다.
- [ ] **실행 가능한 롤백 완성:** 유지보수를 유지한 채 신규 서비스·소켓 정지와 cgroup 확인, journal·gate hold·작업 DB·변경 데이터 및 systemd 기록 보존, 미완료 작업과 모델 health 확인, 검증된 기존 코드·데이터·환경·unit의 호환 단위 복원, 기존 gate pause 및 Client 키 복원을 연결한다. 부분 설치 실패와 불확실한 Caddy reload의 복구도 포함한다. 신규 모델 제어 코드와 unit 설치 기록을 어떻게 보존·정리할지도 확정한다.
- [ ] **Fedora 격리 환경 최종 흐름 시험:** 위 실제 어댑터와 시험 Caddy·가짜 Studio/gate/Client/llama를 연결해 준비부터 수동 Client 재시작, 유지보수 해제까지 한 번에 확인한다. 설치 중·기동 후 실패 시 롤백과 기록 보존도 확인한다. 모의인 조건과 실제 systemd·SELinux를 사용한 조건을 결과에 명시한다.
- [ ] **최종 변경 기준 검증:** 필요한 백엔드·배포 스크립트 회귀와 Ruff, 프런트엔드 lint·빌드, 아티팩트 내용 검사를 최종 커밋 기준으로 수행한다. 수정하지 않은 개별 시험은 관련 위험이나 변경이 있을 때만 다시 실행한다.
- [ ] **GitHub Actions 통합 배포 완성:** 인증된 워크플로 실행의 커밋·아티팩트 해시를 독립적으로 확인하고, 비 Git 운영 서버에 SSH로 전달해 검증·실행할 방법과 수동 Client 재시작 경계를 구현한다. 현재 후보 워크플로는 아티팩트만 생성한다.
- [ ] **기존 자동 배포 차단 확인:** 로컬 Studio 전용 워크플로는 실패하도록 수정됐지만 원격 GitHub 적용 여부는 미확인이다. 최종 코드 커밋·반영 후 원격에서 실제로 자동 배포가 비활성인지 확인한다. 사용자는 이전 중 Client 자동 배포가 겹치지 않도록 관리한다.
- [ ] **운영 직전 점검과 실행 안내 확정:** 운영자가 최근 gate 인증·기존 pause·요청 수, 서비스와 포트, 현재 모델 health 및 유지보수 조건을 다시 확인한다. 사용자가 단계별로 실행할 정확한 명령·예상 출력·중단 및 복구 절차를 확정한다. 집 내부 SSH는 `192.168.0.57:22`, 외부는 `yeppyshiba.iptime.org:2222`다.
